# AI 프론트엔드 컨벤션·리뷰 문서 정비 계획

- 작성일: 2026-10-18
- 조사 기준: `BOM-1257-프론트엔드-컨벤션-정리`, HEAD `06d9bc65`
- 상태: 실행 전 계획. 아래 구조와 정책 변경은 제안이며, 현재 적용되는 규칙이 아니다.
- 이번 산출물: 현황 진단과 실행 계획. 기존 문서 삭제, 컨벤션 변경, CI 변경은 후속 작업이다.

## 1. 목표와 성공 기준

프론트엔드 맥락을 모르는 팀원도 AI와 함께 작업할 때 **필요한 규칙과 서비스 계약을
찾고, 구현하고, 검증하고, 리뷰 결과를 판단할 수 있는 경로**를 만든다.

문서의 양이나 AI의 무오류를 목표로 삼지 않는다. 다음 결과로 성공을 판단한다.

1. 같은 규칙의 원본이 하나이고, 구현 AI와 리뷰 AI가 같은 원본을 읽는다.
2. 작업 유형별로 읽을 문서·참고 구현·검증 방법이 연결된다.
3. 삭제한 파일마다 고유 내용의 처리와 호출 경로 확인 근거가 남는다.
4. 중요한 서비스 계약을 깨는 변경을 정해진 평가 사례에서 탐지한다.
5. 기계적으로 판별 가능한 필수 규칙은 실제 CI 검사와 연결된다.
6. 문서·코드가 달라졌을 때 누가 언제 무엇을 갱신하는지 정해져 있다.

## 2. 범위와 작업 흐름

### 범위

- 저장소에서 추적 중인 컨벤션·AI 지침·리뷰 문서와 이를 소비하는 skill, script, workflow.
- 공통 진입점은 전체 workspace를 대상으로 점검한다.
- 상세 컨벤션과 평가의 첫 적용은 `web` 중심으로 진행하고, `admin`·`maeil-mail`의
  차이를 확인한 후 공통 규칙으로 확장한다.
- `shared`는 웹 공용 UI 및 API 계약, `app`은 WebView 경계와 기존 지침 연결을 확인한다.
  React Native 전용 컨벤션 전면 신설은 별도 작업으로 둔다.
- 기존 구현은 규칙의 근거와 반례를 찾는 데 사용한다. 전체 코드 일괄 교정은 별도 PR로 분리한다.
- 개인 전역 설정과 untracked 문서는 삭제 대상에서 제외한다. 연결된 외부 리뷰 설정은
  실제 접근 가능한 범위에서 별도 확인한다.

### `ask-matt`에 따른 진행 경로

이번 작업은 기존 코드베이스를 바탕으로 정책을 정하고 여러 번에 나누어 실행하는 작업이다.
따라서 **현황 조사 → `/grill-with-docs`로 핵심 판단 확정 → 명세·작은 실행 이슈 →
이슈별 구현·검증** 흐름이 맞는다.

이번에는 요청한 계획을 먼저 작성한다. 인터뷰에서는 코드로 확인 가능한 사실을 다시
묻지 않고, 아래 10절의 정책 결정만 다룬다. `ask-matt`가 안내하는 `/to-prd`·`/to-issues`는
현재 제공된 스킬 목록에 없으므로 실행을 전제로 두지 않는다. 이 문서의 실행 단위를
기준으로 로컬 명세·이슈 초안을 만들 수 있으며, 실제 사용 시 설치된 스킬을 확인한다.
별도 `CONTEXT.md`를 만들더라도 정비 프로젝트의 결정 기록만 담고 서비스 원본을 복제하지 않는다.

않고 구현 diff와 검증 결과로 확인한다. 후속 평가에서는 구현·리뷰 양쪽의 실제 문서 로딩을 점검한다.

## 5. 불필요한 파일을 판단하는 절차

각 파일에 대해 다음 표를 채우고, 변경 PR에서 삭제 근거로 사용한다.

| 파일           | 역할·소비처                     | 고유 내용           | 코드와 충돌      | 처리                     | 이전 위치·삭제 근거        | 검증           |
| -------------- | ------------------------------- | ------------------- | ---------------- | ------------------------ | -------------------------- | -------------- |
| 조사 대상 경로 | 자동 로딩·링크·script·외부 설정 | 남겨야 할 규칙·사례 | 있음/없음/미확인 | 유지/수정/통합/보관/삭제 | 원본 링크 또는 불필요 이유 | 참조·실행 확인 |

삭제는 다음을 모두 확인한 뒤 실행한다.

1. tracked 파일과 symlink를 구분하고, 저장소 내 참조·실제 호출부를 검색한다.
2. 규칙·반례·의사결정 이력이 있다면 새 원본에 옮기거나 보관 이유를 명시한다.
3. 현재 workflow·skill에서 호출하지 않는지 확인한다. 외부 routine 소비 여부가 불명확하면
   ‘미사용 확정’으로 분류하지 않는다.
4. 참조 수정과 내용 이전을 같은 PR에서 처리한다.
5. 정비 후 링크·명령·문서 로딩을 검증한다.

**참조가 없거나 오래됐다는 이유만으로 삭제하지 않는다.** 특히 호환 진입점, symlink,
과거 오류의 반례는 삭제해도 되는 중복 문서와 다르다.

## 6. 컨벤션을 재검토하는 방법

기존 컨벤션을 전부 유지하거나 전부 새로 쓰지 않는다. 다음 항목을 규칙별로 정리한다.

- 식별자·제목, 해결하려는 문제, 적용 workspace·작업 조건.
- 강도: 필수 / 권장 / 참고. 필수 위반과 리뷰 심각도는 별개로 판정한다.
- 구체적 기준, 허용 예외, 정상 예시와 위반 예시.
- 근거: 현재 코드·테스트·리뷰 사례·기술 문서·팀 결정.
- 검증 수단: lint / type-check / focused test / UI 확인 / AI 맥락 검토.
- 상태: 유지 / 수정 제안 / 폐기 제안 / 추가 확인, 마지막 확인일과 담당 역할.

라이브러리 동작에 의존하는 규칙은 설치 버전을 확인하고 Context7에서 공식 문서를
조회한다. 팀의 취향을 프레임워크의 필수 제약이라고 설명하지 않는다.

### 우선 검토할 주제

1. **상태와 effect**: 서버·UI·파생 상태 구분, 동기화의 목적, 의존성 직렬화 규칙,
   반환값의 참조 안정성이 필요한 소비 조건.
2. **데이터와 오류**: query factory, query key, mutation invalidation, 중복 제출,
   로딩·빈 결과·실패·재시도·성공 피드백, mock 동기화.
3. **컴포넌트 경계**: 책임·재사용 범위, 과분리의 반례, route/export 예외,
   shared 웹 UI에 적용할 범위.
4. **UI**: theme 사용, device 판단, 접근성, 입력·disabled·오류 상태.
5. **선언 순서·네이밍**: 기존 규칙과 도구가 충분한지 판단. 실익 없는 신규 형식 규칙은 늘리지 않음.

사용자가 제시한 `useSuspenseQuery` 일괄 사용과 `Suspense`·`ErrorBoundary` 강제는
**검토 후보**다. 현재 확정된 정책으로 취급하지 않는다. 데이터 로딩 방식별 적용 조건,
예외, 경계 위치와 복구 흐름을 먼저 정의한 뒤 자동화 가능성을 판단한다.

## 7. 서비스 맥락과 리뷰 설계

### 서비스 맥락 문서의 최소 항목

처음에는 읽기·기록, 인증·WebView처럼 영향이 큰 흐름부터 작성한다.
챌린지·구독 등은 실제 변경 빈도와 회귀 사례를 보고 순차 확대한다.

- 사용자가 하려는 일과 정상 흐름, 제품 용어.
- 유지해야 할 계약과 상태 전이. 구현으로 확인한 사실과 제품 의도를 구분.
- 비로그인·빈 데이터·오류·재진입·브라우저/앱 차이.
- entry route → page → hook → API → 공유 코드의 주요 경로.
- 변경 시 같이 확인할 소비처·mock·test와 기존 회귀 사례.
- 근거 경로, 확인일, 미확인 사항. 백엔드 계약은 프론트 코드만으로 단정하지 않음.

### 리뷰 절차

1. PR 의도, base/head, 변경 workspace와 작업 유형을 확정한다.
2. 공통 리뷰 정책과 해당 컨벤션·도메인 문서를 읽는다.
3. diff에서 시작하되 head 기준 파일 전체와 직접 의존성·소비처를 확인한다.
4. 공유 계약을 바꿨다면 workspace 경계를 넘어 소비처를 확인한다. 동명 symbol만으로
   무관한 workspace를 영향 범위에 넣지 않는다.
5. 기존 이슈와 이번 변경이 도입한 문제를 구분하고, 반례·기존 보호 장치를 확인한다.
6. finding에 발생 조건 → 사용자 영향 → 코드 근거 → 검증 방법을 남긴다.
7. 검사하지 못한 영역과 미실행 테스트를 명시한다. finding 0개를 완전 검증과 동일시하지 않는다.

컨벤션 검토와 서비스 동작 검토는 관점을 나누되, 별도 에이전트나 새 자동화 시스템이
필수는 아니다. 규칙 위반은 원본 규칙을 인용하고, 단순 취향 제안은 필수 수정으로 올리지 않는다.
generated 파일은 내용을 일반 코드처럼 리뷰하지 않되 generator·입력 계약·소비 코드와
재생성 일치 여부로 검증한다. 생성물 diff만 보고 수동 편집이라고 단정하지 않는다.

### 리뷰 실행 방식의 결정

초기에는 기존 `ai-review-workflow`의 실행 경로를 정리해 재사용하는 안을 우선한다.
자동 리뷰가 이미 외부에서 동작하는지는 먼저 확인한다. 수동 실행과 PR 자동 실행은
같은 리뷰 정책을 읽게 하고, 정책 파일을 각각 복제하지 않는다.

자동 실행 도입은 평가 결과와 비용·지연·중복 리뷰를 확인한 뒤 결정한다.
AI 검토 결과, GitHub의 `APPROVE`, 실제 merge 가능 여부는 각각 분리해 설계한다.
AI 리뷰만으로 merge할 수 있는 변경 범위와 사람이 판단해야 하는 계약 변경은 팀이 정한다.

## 8. CI 적용과 평가

### CI 강제의 우선순위

| 종류                  | 적용 방향                               | 완료 증거                                 |
| --------------------- | --------------------------------------- | ----------------------------------------- |
| 기존 lint·type-check  | workspace별 실제 실행과 누락 확인       | 로컬 명령·PR workflow·required check 매핑 |
| 문서 링크·경로·명령   | 변경 문서에 대한 가벼운 검사부터        | 깨진 링크·없는 script를 넣었을 때 실패    |
| 명확한 정적 규칙      | 기존 lint rule로 표현 가능한 항목부터   | 정상·위반·허용 예외 fixture 통과          |
| API·캐시·상태 전이    | 위험한 계약의 focused test              | 회귀를 넣으면 실패하고 정상 구현은 통과   |
| UI·Suspense·오류 경계 | 관련 흐름의 컴포넌트/E2E 또는 수동 확인 | 로딩·실패·복구 시나리오 결과              |
| 책임 분리·도메인 영향 | AI 리뷰와 제한된 사람 판단              | 근거 있는 finding과 오탐 검증             |

새 규칙은 기존 위반 수와 예외를 조사한 뒤 적용한다. 기존 위반은 별도 정리 범위로
기록하고 신규 위반부터 제한하는 방법을 검토한다. 경고 상태에서 확인한 규칙을
차단 규칙으로 올릴 때는 정상 사례가 막히지 않는지 검증한다.
CI 파일이 존재하는 것과 merge를 차단하는 required check인 것은 구분해 확인한다.

### 고정 평가 사례

실제 과거 PR·회귀 사례를 우선 사용하고, 부족한 사례는 로컬 fixture로 보완한다.
평가 전에 정상/위반/예외 정답과 근거를 정해 모델 응답에 따라 정답이 바뀌지 않게 한다.

| 사례                                                     | 기대 결과                                                 |
| -------------------------------------------------------- | --------------------------------------------------------- |
| query 조건 변경 후 key/소비 화면/캐시 처리가 누락된 변경 | 실제 사용자 영향과 관련 경로를 찾아 지적                  |
| mutation 성공 후 특정 화면에 이전 데이터가 남는 변경     | 누락된 갱신 대상과 재현 조건 확인                         |
| WebView message의 한쪽 계약만 바뀐 변경                  | 송수신 양쪽의 불일치 탐지                                 |
| admin의 기존 외부 adapter 사용                           | 공용 fetcher 규칙으로 오탐하지 않음                       |
| 허용된 route export·generated output 변경                | 예외와 생성 근거를 확인하고 일반 컨벤션으로 오탐하지 않음 |
| 동명 hook이 다른 workspace에 존재하는 변경               | 실제 공유 관계가 없으면 영향 범위를 부풀리지 않음         |
| 단순 UI 수정                                             | 필요한 규칙을 찾고 로딩·오류·접근성 확인 범위를 판단      |
| 정상 변경·관련 없는 과거 결함                            | 새로운 문제를 억지로 만들지 않음                          |

문서 변경 전후에 같은 사례·가능한 같은 모델 설정으로 평가하고, 최소 2회 반복해 흔들림을
기록한다. 기대 탐지 누락, 오탐, 읽은 문서, 소요 시간, 사용량을 비교한다.
초기 완료 조건은 선정한 필수 회귀 사례의 탐지와 허용 예외의 오탐 0건이다.
작은 평가 세트의 통과를 전체 서비스 안전 보장으로 해석하지 않는다.

프론트엔드 비전문 팀원에게 대표 작업 1건을 문서만으로 진행하게 하여, 어떤 파일을 읽고
수정·검증해야 하는지 스스로 찾는지도 확인한다. 막힌 지점은 문서 연결 또는 규칙의
누락으로 기록하고 개선한다.

## 9. 실행 단위와 완료 조건

각 단계는 독립적으로 검토 가능한 변경으로 나눈다. 표의 담당자는 역할 제안이며 실제
사람 배정은 팀에서 정한다. AI는 조사·초안·기계 검증을 맡고, FE 담당자는 논쟁적인
컨벤션·계약 결정에 집중하도록 한다.

| 순서 | 작업·대상                                | 산출물                                              | 선행 조건         | 완료 조건                                                 |
| ---- | ---------------------------------------- | --------------------------------------------------- | ----------------- | --------------------------------------------------------- |
| 1    | 문서·skill·workflow·외부 소비처 목록화   | 5절의 파일별 처리표, 충돌 목록, 현재 리뷰 실행 지도 | 없음              | 모든 정리 후보에 역할·근거·미확인 사항 기록               |
| 2    | stale 안내·중복·빈 기록 정리             | README·리뷰 스킬 정합성 수정, 근거 있는 통합/삭제   | 1                 | 살아 있는 호출 경로 유지, 링크·고유 내용 유실 없음        |
| 3    | FE 컨벤션 재검토·주제별 분리             | 규칙별 판단표, 컨벤션 문서와 색인                   | 1, 정책 결정      | 조건·예외·검증 수단 명시, 리뷰 전용 구현 규칙 해소        |
| 4    | 서비스 context 최신화·고위험 도메인 연결 | context 원본과 관련 skill 참조, 도메인 문서         | 1, 제품 사실 확인 | 코드 근거·제품 의도·출시 상태 구분, 복제 원본 없음        |
| 5    | 리뷰 입력·범위·보고 기준 통합            | REVIEW·스킬·팀 사용 안내                            | 2~4               | 같은 규칙 로딩, 호출부 추적, 오탐 예외 반영               |
| 6    | 기계 검사 보완                           | 필요한 lint/test/CI 변경, 규칙→check 표             | 3                 | 정상·위반·예외 검증, 기존 failure 분리, 실제 PR 실행 확인 |
| 7    | 고정 사례 평가·팀원 시범 사용            | 변경 전후 결과, 남은 누락·오탐, 운영안              | 5~6               | 8절 초기 완료 조건 충족, 정책 결정 및 유지 담당 확정      |

1단계에서 변경 전 평가 기준도 확보한다. 3·4단계는 경계가 확정되면 별도 작업으로 진행할
수 있다. 자동 리뷰 트리거 신설·merge 정책 변경은 7단계 결과를 보고 별도 변경으로 다룬다.

### 각 변경의 검증

- 문서: `git diff --check`, 수정 링크·경로·명령·저장소 사실 확인.
- 규칙 이전: 이전 규칙과 새 원본을 대조해 유실·복제·의미 변경 확인.
- skill: 대표 작업에서 필요한 문서가 로딩되는지 확인.
- 코드·설정: [AI behavior rules](ai-rules.md)의 해당 검증 적용.
- publisher 변경 시: 외부 게시 호출을 stub한 로컬 mock으로 형식·event를 검증.
  가짜 PR에 실제 API 호출을 보내는 방식은 검증 수단으로 사용하지 않는다.
- 평가 결과는 로컬 기록으로 남기고, 실제 PR에 시험용 finding을 게시하지 않는다.

## 10. 실행 중 확정할 결정

확인 가능한 사실을 먼저 조사한 후 아래 항목만 짧게 결정한다. 이 계획 작성에는
답변이 필요하지 않으며, 해당 정책을 적용하는 단계 전에 확정한다.

| 결정               | 초기 제안                                             | 판단 근거·담당 역할                           |
| ------------------ | ----------------------------------------------------- | --------------------------------------------- |
| 첫 상세 적용 범위  | web 중심 + 공유 계약, 다른 웹 workspace 예외 확인     | 변경 빈도·회귀 사례 / FE 담당                 |
| 논쟁적인 기존 규칙 | 즉시 전면 변경 대신 규칙별 유지·수정·폐기             | 공식 문서·반례·비용 / FE 담당                 |
| context 원본 위치  | 도구 중립적인 docs로 이전                             | 기획·구현·리뷰의 공동 소비 / 제품·FE 담당     |
| 리뷰의 강도        | 필수 컨벤션 위반과 동작 버그를 구분, 취향 제안 최소화 | 과거 유효 finding·오탐 / FE 담당              |

## 11. 최신 상태를 유지하는 운영 방식

- 컨벤션·도메인 계약 변경자는 같은 PR에서 원본 문서를 갱신한다. 변경이 없으면
  ‘문서 영향 없음’의 짧은 이유를 남긴다.
- PR 템플릿에는 적용 규칙·관련 서비스 계약·수행한 검증·문서 영향의 링크만 추가한다.
  규칙 본문을 다시 복제하지 않는다.
- 잘못된 AI 지적은 발생 조건과 반례를 `false-positives.md`에 남긴다. 답글이 없다는
  이유만으로 수용된 규칙으로 승격하지 않는다.
- 실제 반복 회귀는 테스트 또는 구현 규칙으로 옮기고, 리뷰 전용 필수 규칙으로 쌓지 않는다.
- 초기 2주 또는 실제 PR 5건을 적용 단위로 삼아 누락·오탐·검토 시간을 점검한다.
  이후 정기 점검 간격은 팀 부담에 맞게 조정한다.
- 정비 완료 후 이 문서는 계획·결정 이력으로 보관하며, 새 작업의 필수 지침으로 로딩하지 않는다.

참고 도구인 [Claude MD Management](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/claude-md-management)는
공식 README상 CLAUDE.md 점검과 세션 학습 반영을 제공한다. 선택적 문서 로딩이나 규칙
준수를 보장하는 수단으로 가정하지 않는다. 기존 진입 구조를 정리한 후 유지보수에 실제로
도움이 되는지 비교하고, 설치는 이번 계획의 선행 조건으로 두지 않는다.
